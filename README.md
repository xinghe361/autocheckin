# 自动签到（Docker）

每天自动帮你在网站上签到，支持失败重试、连续失败后自动用 DeepSeek 分析、通知推送、
WebDAV 备份，以及**录制你的操作**来新增任意站点。

内置三个站点：**V2EX 每日铜币**、**NodeSeek 试试手气**、**Chiphell 每日邪恶值**。

![Platform](https://img.shields.io/badge/platform-linux%2Famd64-lightgrey)
![Python](https://img.shields.io/badge/python-3.12-blue)
![Tests](https://img.shields.io/badge/tests-450%20passed-brightgreen)

**特点一览**

| | |
|---|---|
| 部署 | 一个 `docker-compose.yml`，host 网络模式开箱可用 |
| 新增站点 | 网页上点「开始录制」，在浏览器里点一遍签到，之后照着回放 |
| 调度 | 每天固定时刻，或**以上次成功时刻为基准**；都可叠加 **±1 小时**随机 |
| 失败处理 | 重试次数/间隔可配；连续失败达阈值调 **DeepSeek** 分析并保存新方案 |
| AI 兜底 | 连 AI 分析也失败 → **自动停用该站点**并推送告警 |
| 通知 | pushplus / 企业微信 / Telegram；全部 / 仅失败 / 仅成功 / 自定义站点 |
| 代理 | 全站统一走代理；**每个通知渠道可单独选走不走** |
| 备份 | WebDAV，支持配置恢复；密钥可单独备份 |
| 安全 | 默认需登录、凭据 Fernet 加密、容器带 `no-new-privileges` |
| 依赖 | 除 `cryptography` 外**全为标准库**（**不含浏览器**，见下） |
| 镜像 | 约 0.2GB（基础镜像 `python:3.12-slim`，不带浏览器） |

> **关于浏览器**：内置站点全部走**纯 HTTP 请求**，不需要浏览器；
> 抓 Cookie 靠你自己浏览器里的扩展，录制脚本也注入在你自己的浏览器里。
> 所以镜像里**故意不带浏览器**（带了会多 600MB+，而移除它的唯一办法
> 是换基础镜像 —— 在后面层里 `rm` 并不会减小体积）。
> 只有"录制的自定义站点"需要浏览器，那种情况下会明确报
> "需要浏览器但不可用"。**需要时怎么加**：[见下文](#需要浏览器怎么办)。

> **已在真实极空间 Z4 上验证**：镜像构建成功、容器 2 秒就绪、
> 页面与接口正常、凭据不回显。

## 一、快速开始（极空间 NAS）

### 1. 用 Compose 启动（推荐 host 网络模式）

在极空间 Docker 界面新建「编排 / Compose」，粘贴 [docker-compose.yml](docker-compose.yml)
的内容，启动。核心就这几行：

```yaml
services:
  autocheckin:
    image: xinghe361/autocheckin:latest
    container_name: autocheckin
    restart: unless-stopped
    network_mode: host
    security_opt:
      - no-new-privileges:true
    shm_size: "256m"
    environment:
      - TZ=Asia/Shanghai
      - PORT=28999
      - DATA_DIR=/data
    volumes:
      - ./data:/data
```

不需要代理就选「直连」（默认），程序按**全部直连**跑。

> **代理只在网页上配**：「设置 → 网络 → 联网方式」选「走代理」再填地址。
>
> 环境变量 `PROXY` **已不再生效**（compose 里也不需要写这一行）。
> 为什么去掉：两处都能设会互相打架，而"网页里改完却不生效"是最难排查的
> 一类问题。现在只有一个权威来源，行为可预测。
>
> ⚠️ **别留着模板里的占位符**。像 `http://你的代理地址:7890` 这种没替换的地址，
> 程序会把它当真实主机名去解析，报错显示为"域名解析失败"，
> 看起来像 DNS 故障 —— 实测很容易被带偏。
> 现在程序启动时会识别出占位符并明确警告，然后按直连运行。

> **`./data` 是相对路径**，相对 compose 文件所在目录。也就是说数据会落在
> 与 compose 文件同级的 `data/` 文件夹里 —— 整个文件夹可以整体搬走，
> 不会像命名卷那样藏在 Docker 自己的目录里。
>
> ⚠️ **容器侧必须写 `/data`**（要和 `DATA_DIR` 一致）。
> 写成 `/app/data` 的话数据会写进容器内部，**重建容器就全丢**。

**两种模式对比**：

| | **host 模式（推荐）** | 桥接模式 |
|---|---|---|
| 配置 | `network_mode: host`，**不要写 `ports:`** | `ports: "28999:28999"` |
| 访问地址 | `http://NAS的IP:28999/` | `http://NAS的IP:28999/` |
| 端口怎么定 | 容器内部监听什么就是什么（镜像默认 **28999**） | 改冒号左边即可 |
| 出网 | 直接走宿主网络 | 多一层 NAT |

> **为什么默认 28999**：host 模式下 `ports:` 映射**完全无效**，容器直接占用宿主端口。
> 而 `8080` 在 NAS 上通常已被系统服务占用，撞上会直接报 `Address already in use`。
> 所以镜像内部默认就监听 28999，host 模式开箱可用。想换端口改 `PORT` 即可。

如果界面上找不到 Compose，也可以直接「添加容器」：

| 项 | 值 |
|---|---|
| 镜像 | `xinghe361/autocheckin:latest` |
| 网络 | **host** |
| 端口 | 不需要填（host 模式） |
| 卷 | **容器侧填 `/data`**（装载路径栏会自动填好）；宿主侧点「添加文件夹」选一个目录 |
| 环境 | `TZ=Asia/Shanghai`、`PORT=28999`、`DATA_DIR=/data`（代理改为只在网页里配）|

> **关于数据目录**
>
> 镜像里声明了 `VOLUME ["/data"]`，所以**容器侧（装载路径）会自动填好 `/data`**，
> 你不用打。要决定的是**宿主侧放在哪**：
>
> | 做法 | 数据在哪 | 适合 |
> |---|---|---|
> | Compose 里用 `./data:/data` | 与 compose 文件同级的 `data/` 目录 | 想整体搬走、直接看得到 |
> | 点「添加文件夹」选一个目录 | 你自己的共享文件夹里 | 想放到某块特定数据盘 |
> | 不添加挂载 | Docker 命名卷里（自动创建） | 完全不想管 |
>
> **都行**，因为容器里 `DATA_DIR=/data`，只要卷挂到 `/data` 就落盘。
>
> ⚠️ **两个容易犯的错**：
> 1. **宿主侧别选 `/data/...`** —— 那是系统分区，空间很小
>    （实测该 NAS 的 `/` 只剩几百 MB），写满会影响整台 NAS。
>    极空间的盘符是"每块磁盘一个"（形如 `/data_XXXXXXXX/data/`）。
> 2. **容器侧别写成 `/app/data`** —— 那和 `DATA_DIR=/data` 不是同一个目录，
>    数据会写进容器内部，**容器一重建就全丢**。
>    （容器里代码在 `/app/app`，很容易顺手写错。）
>
> 用命名卷时的备份命令写在 [docker-compose.yml](docker-compose.yml) 注释里；
> 用 `./data` 的话直接复制那个文件夹即可。

### 2. 打开网页界面

`http://NAS的IP:28999/`

### 3. 填设置 → 配登录 Cookie → 启用站点

1. 「设置」页填：**代理** → **通知** → **WebDAV**（可选）→ **DeepSeek**（可选）。
2. 「站点」页给**每个站点配一次登录 Cookie**（见下一节）。不配的话站点拿到的是
   未登录页面，签到必然失败 —— 这是最常见的失败原因。
3. 点该站点的「立即」试跑一次，确认没问题再放开日常自动签到。

> 首次建议先用 `--no-scheduler` 启动（只开界面不自动签到），把配置填完再放开。

### 4. 怎么给站点配登录 Cookie

点站点右侧的「**编辑**」，表单会在**该站点下方展开**，找到「🔑 登录状态」。

有两条路，任选其一：

#### 方式一：一键从浏览器读取（推荐，能拿到 HttpOnly 字段）

用现成的开源扩展 [qd-today/get-cookies](https://github.com/qd-today/get-cookies)
（QD 项目官方维护）。它用浏览器特权接口读 Cookie，**能读到 HttpOnly 的登录字段**。

1. 点表单里的「**📖 怎么用？**」，按弹窗里的三步走：
   * **装扩展**：Chrome/Edge 商店或 Firefox 商店（弹窗里有直达链接）
   * **让扩展在本容器生效**：打开扩展的**选项页**，把弹窗里给出的容器地址
     （形如 `http://<你的NAS地址>:28999`）**填进去**。
     ⚠️ **这一步最容易漏** —— 扩展默认只认 QD 的地址，不填的话点按钮毫无反应。
   * **回来点**「⚡ 从浏览器读取 Cookie」→ 扩展弹确认框 → 确定 → 自动保存
2. 保存后点「**检查是否有效**」确认。

> 扩展的通信方式是它注入到本页面的脚本监听
> `[data-toggle="get-cookie"]` 的点击，再 `window.postMessage` 把 Cookie 交回来。
> 本容器做的就是承接这一段：放好那个按钮 + 监听消息 + 存库。

#### 方式二：手动粘贴（不想装扩展时）

1. 用**你自己的浏览器**打开该网站并登录（你平时怎么登就怎么登）。
2. 按 **F12** → 切到 **Network** 标签 → 按 **F5** 刷新。
3. 点列表里**第一条请求** → **右键** → **Copy** → **Copy as cURL**。
4. 把整段**原样粘贴**进表单里的输入框，点「**保存 Cookie**」。

粘贴什么格式都能识别，不用你自己整理：

| 你可以粘 | 说明 |
|---|---|
| Copy as cURL 的**整段** | 最省事，自动从里面提取 Cookie |
| `a=1; b=2` 这种 Cookie 串 | 直接用 |
| DevTools 里一行一个的键值列表 | 直接用 |
| `cookies.txt`（Netscape 格式） | 直接用 |

> **为什么登录字段一定要用上面两种办法拿？**
> 关键登录字段（如 V2EX 的 `PB3_SESSION`、Discuz 的 `auth`）都带 `HttpOnly`
> 标记，**JavaScript 读不到** —— 实测确认过。
> 所以控制台里的 `document.cookie`、以及任何油猴脚本都拿不到它们；
> 只有浏览器扩展的特权接口、或 DevTools 的 `Copy as cURL` 才能拿到完整登录态。

配好后：

* **「检查是否有效」**：立刻验证并告诉你是"有效 / 已失效 / 无法判断"。只做只读请求，**不会触发签到**。
* **「清除」**：删掉该站点的登录态。
* **失效会自动提醒**：后台每天巡检一次，**只在"有效→失效"那一刻**推一条通知
  （不重复刷屏），你就能主动去更新，而不是等签到失败才发现。

## 二、安全设计

**默认需要登录。** 首次访问会引导你设置一个访问口令（至少 6 位），
之后用该口令进入网页界面。口令只用于本界面，与你的各站点账号无关。

| 措施 | 说明 |
|---|---|
| 访问控制 | 默认开启；口令加密存储，会话令牌只存 SHA-256 哈希 |
| 令牌传递 | HttpOnly + SameSite=Lax Cookie，不放在 URL 里 |
| 登录限速 | 5 分钟内失败 10 次即拒绝 |
| 凭据存储 | Fernet 加密（AES-128-CBC + HMAC），文件权限 600 |
| 界面回显 | 所有凭据只显示打码形式，绝不回显明文；Cookie 只回显**字段名**，不回显值 |
| 密钥备份 | **单独文件**，不与备份对象合并；是否上传由你显式勾选 |
| 容器加固 | 默认带 `no-new-privileges:true` 与 `shm_size: 256m` |
| 依赖 | 除 `cryptography` 外**全部为标准库**（不含浏览器） |

提交前可自查：

```bash
python selfcheck.py            # 敏感文件 / 编码 / 关键文件完整性
python docs/check_compose.py   # compose 结构校验（缩进、关键字段）
```

### 使用上的三点建议

1. **首次启动后请立刻打开网页完成口令初始化**，不要让它长时间停留在未设置状态。
2. **不要把本服务的端口暴露到公网**，它设计为在内网使用。
3. 若确实需要公网访问，请在设置里关掉「允许内网 WebDAV 地址」。

更完整的设计说明见 [docs/SECURITY.md](docs/SECURITY.md)。

## 三、核心功能

### 调度：两种方式，每站点独立

| 方式 | 行为 |
|---|---|
| **每天固定时刻** | 设 03:00 就是每天 03:00；今天已过则顺延明天 |
| **以上次成功时刻为基准** | 今天 03:21 成功 → 明天 03:21；明天 03:50 成功 → 后天 03:50 |

两种都能叠加 **±1 小时内的随机偏移**（可调范围，上限 1 小时）。

### 失败处理

1. 失败后按配置**重试**（次数 + 间隔可调，默认 3 次 / 30 分钟）
2. 连续失败达到阈值 → 调 **DeepSeek 分析**，产出新的选择器/关键词/步骤
3. 分析成功后**自动保存**并用于之后的签到
4. **如果分析本身也连续失败**（默认 2 次）→ **自动停止该站点签到**并推送"分析失败"告警
5. 每天调用分析次数有上限，避免持续故障时无限消耗额度

### 通知

支持 **pushplus / 企业微信机器人 / Telegram**，可多选。

- 策略：**全部** / **仅失败** / **仅成功** / **自定义站点** / 不通知，且每站点可单独覆盖
- **每个渠道可单独选择走不走代理**（例如 Telegram 走代理、企业微信直连）；
  没单独设置就跟随「代理设置」里的主代理
- "AI 分析失败、站点被停用"这类**系统级告警不受站点策略限制**，只要配了渠道就会推

### 两种签到时间模式

| 模式 | 含义 |
|---|---|
| **每天固定时刻** | 每天在设定钟点签到一次；今天该时刻已过就顺延到明天 |
| **以「上次签到成功时间」为基准** | 每隔设定间隔签到一次，基准是**上一次真正成功的时间**（不是固定钟点） |

第二种模式的例子：今天 03:21 成功、间隔 24 小时 → 下次明天 03:21 左右。

**还没有成功过的站点**：先等一个间隔，然后去尝试第一次签到；
第一次成功后，基准就自动换成那个真实的成功时间。
所以**不需要额外填一个"初始签到时间"**。

> 以前这里的间隔是写死的 24 小时，界面上却显示"上次成功后 XX 分钟"
> （取的是重试间隔那个值），显示与实际不符、也没法调。现在
> 「间隔（分钟，1440＝24 小时）」是真的生效的，最小 1 小时。

### AI 什么时候被调用、会不会烧 token

**统一逻辑：签到尝试次数只由站点自己的重试设置决定；全局只控制"什么时候调用 AI"。**

| 设置在哪里 | 字段 | 作用 | `0` 的含义 |
|---|---|---|---|
| 站点 → 失败重试 | `retry_count` / `retry_interval_minutes` | **唯一的尝试次数来源**（首次 + 重试） | — |
| 全局 → DeepSeek | `ai_after_failures` | 每连续失败几次调用一次 AI（在整数倍处） | **不启用 AI 分析** |
| 全局 → DeepSeek | `max_calls_per_day` | 每天调用次数的**硬上限** | 不限制（由上面的倍数决定） |
| 全局 → DeepSeek | `fail_threshold` | 连续几次"分析本身失败"后暂停该站点 | 不限制（永不停用） |

调用次数可以直接算：

```
每天最多调用 AI 次数 = floor((重试次数 + 1) / ai_after_failures)
                     再受 max_calls_per_day 封顶
```

**想只调用一次 AI**：把 `ai_after_failures` 设成**大于**该站点的重试次数
（例如站点重试 3 次、一轮最多尝试 4 次，所以设 4 就只会调用一次）。

> 之前这里有三层数字（每站点每天尝试次数、每站点每天调用 AI 次数、
> 全部站点合计调用 AI 次数），互相重叠、还会和站点的重试次数打架
> （默认配置下重试根本做不满）。现已统一：尝试次数归站点，调用时机归全局。
>
> 更早版本的 `max_calls_per_day`（"绝对上限"）与 `ai_calls_per_day` 与本项重叠，
> 都已成为本表的 `max_calls_per_day`，旧配置会自动迁移。

**签到成功会清掉** AI 失败计数与暂停标记。
被自动暂停的站点不会自己恢复（这是刻意的：暂停就是为了停止消耗），
修好后到「站点」页手动「启用」。

### 关于页面刷新（默认不自动刷新）

站点列表**默认不自动刷新** —— 因为填表单时被刷新打断很难受
（表单会被重建、光标丢失、填到一半的内容没了）。

实际上站点数据只在两种情况下变：

| 情况 | 是否自动更新 |
|---|---|
| 你自己的操作（保存、启停、立即执行、删除） | ✅ 这些操作本身就会刷新 |
| 后台调度器跑完签到 | ❌ 需手动点「刷新」 |

调度是按你设的时刻跑的（一般凌晨），填表单时基本不会正好在跑，
所以定时刷新收益很小。想刷新时点「刷新」按钮即可。

如果你确实想要定时刷新：**「设置 → 网络 → 页面自动刷新」**里打开
（默认关闭，存在浏览器本地）。即使打开，**编辑表单期间也会自动跳过**，
不会冲掉你填的内容。



实测 V2EX 直连超时、NodeSeek 直连被拒（域名解析被污染），
而 Chiphell 直连就通。所以代理需要能**按站点**区分。

**全局**（「设置 → 网络 → 联网方式」）：

| 选项 | 行为 |
|---|---|
| 直连（默认） | 全部站点直连，不需要填地址 |
| 走代理 | 用下面填的代理地址 |

**单个站点**（「站点」页 → 该站点「编辑」→「联网方式」）：

| 选项 | 行为 |
|---|---|
| 跟随全局设置（默认） | 全局选直连就直连，选代理就用全局代理 |
| 强制直连 | 这个站点永远直连（哪怕全局配了代理） |
| 用这个代理 | 这个站点单独用下面填的地址 |

> 代理**只**在网页里配（环境变量 `PROXY` 已不再生效）。
> 想改先点页面**顶部的「保存全部设置」**（设置项很长，按钮放在最上面，
> 滚动时也一直可见）。

直连失败时会明确提示"**该站点可能需要通过代理访问**"，
而不是只给一句"连接超时"让人不知道下一步做什么。
如果配了代理还失败，报错会直接指向**代理本身**（地址解析不了 / 代理拒绝连接），
不会误报成 DNS 故障 —— 这两类问题的排查方向完全不同。

### 新增站点：录制你的操作

1. 「新增站点」页填站点标识、名称、主页地址
2. 点「**开始录制**」→ 在浏览器窗口里像平时一样登录并完成一次签到
3. 点「**结束并保存**」→ 操作被整理成步骤（自动合并连续输入、去重相邻点击）
4. 之后每天按这些步骤自动执行

录到的步骤可以直接在界面上编辑（JSON），也可以之后再录一次追加。

> ⚠️ 录到的步骤是 `click` / `fill` / `goto` 这类**浏览器动作**，回放需要浏览器。
> 当前镜像**不含浏览器**，所以录制的站点要用起来，得配 `remote_cdp_url`
> 连接外部 Chrome（见[「需要浏览器怎么办」](#需要浏览器怎么办)）。

### 加站点不用重建镜像（模板插件）

站点模板是**纯数据**，所以放在数据目录里就能加 —— **不用重建镜像**：

1. 复制 `site-plugins/example.json`，改 `id` / `name` / `homepage` / `flow`
2. 把文件放进容器的数据目录：`<数据目录>/templates/<id>.json`
3. 网页「设置 → 可选站点」→ 点「重新扫描」
4. 在列表里**选中**它 → 它才成为你实际签到的站点

| 能力 | 说明 |
|---|---|
| 选中才生效 | 未选中的只出现在"可选"列表里，**不会去签到** |
| 覆盖内置 | 插件 id 与内置相同（`v2ex`/`nodeseek`/`chiphell`）时**插件优先**，站点改版可自己紧急修正 |
| 自动感知 | 按文件修改时间判断，改了文件不用重启 |
| 容错 | 一个不合规的文件只跳过它自己并说明原因，不影响其它 |

**格式与校验规则**见 [site-plugins/README.md](site-plugins/README.md)。
纯请求流程（`get` / `post` / `extract_regex`）开箱可用；用了浏览器动作
必须在文件里显式写 `"need_browser": true`，否则会被校验直接拒绝
（免得你以为走纯请求、实际什么都没做）。

### WebDAV 备份

把配置与运行状态备份到你自己的 WebDAV（云端目录 `autocheckin/`），支持一键恢复。

### 需要浏览器怎么办

镜像**默认不带浏览器**（省 600MB+）。以下情况才需要浏览器：

- 你录制的**自定义站点**（录制产出的是 `click` / `fill` / `goto` 这类
  浏览器动作，纯请求只支持 `get` / `post` / `extract_regex`）
- 模板插件里声明了 `need_browser: true` 的站点

**两条路，优先推荐第一条**（镜像仍然很瘦）：

#### 路线一：连接外部已有的 Chrome（推荐）

`playwright` 包已内置，所以**不需要往镜像里装浏览器** —— 只要把
`remote_cdp_url` 指向一个开着调试端口的 Chrome（比如 NAS 上的 Kasm Chrome）：

1. 让那个 Chrome 带 `--remote-debugging-port=9222` 启动
2. 网页「设置」里把 `remote_cdp_url` 填成 `http://<地址>:9222`
3. 重启容器（这个地址在启动时读取）

好处：登录态在外部 Chrome 里长期保留，不用每次注入 Cookie。
注意：那个 Chrome 得一直开着；调试端口**不要暴露到公网**。

> 实测记录：NAS 上常见的 Kasm 版 Chrome **默认不开 9222**
> （只暴露 6901/VNC 端口），需要按它的文档加上启动参数。

#### 路线二：换回带浏览器的基础镜像

```dockerfile
FROM mcr.microsoft.com/playwright/python:v1.48.0-noble
# ... 其余不变
```

> ⚠️ **别只加 `rm -rf /ms-playwright/firefox-*` 这类删除来"瘦身"**：
> 在后面层里删文件不会减小镜像体积（文件仍在基础镜像的层里，
> 拉取时照样要下载）。实测确认：浏览器所在层 616MB 原封不动。
> 要减小体积，只能**不用带浏览器的基础镜像**。

不用浏览器时的行为：需要浏览器的站点会明确报
"该站点需要浏览器……但当前镜像没有浏览器"，**内置站点完全不受影响**。
也可以用 `DISABLE_BROWSER=1` 显式关掉浏览器功能。

## 四、环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `28999` | **容器内部**监听端口。host 模式下它就是宿主端口；桥接模式下改 compose 里 `ports` 左边即可 |

> **端口相关的常见困惑**
> - **host 模式**：容器内部端口 = 宿主端口。镜像默认监听 28999，直接访问 `http://NAS的IP:28999/`
> - **桥接模式**：`ports: "28999:28999"` 含义是 *宿主 28999 → 容器 28999*；只改左边那个数字就能换宿主端口
> - 容器内往外访问自己用 `127.0.0.1:$PORT`；健康检查也是走容器内部，改宿主端口不影响它
> - ⚠️ **host 模式下写 `ports:` 是无效的**（Docker 会忽略），端口由 `PORT` 决定
| `DATA_DIR` | `/data` | 配置、密钥、状态存放目录（**必须持久化**） |
| `TZ` | `Asia/Shanghai` | 时区，影响签到时间的解释 |
| ~~`PROXY`~~ | — | **已废弃**：代理改为只在网页「设置 → 网络」里配 |
| ~~`APP_VERSION`~~ | — | **已废弃**：版本号只反映代码真实版本，不可覆盖 |
| `TICK_SECONDS` | `60` | 调度检查间隔（最小 5 秒） |
| `NO_SCHEDULER` | 空 | 设为 `true` 则只开界面、不自动签到 |
| `AUTOCHECKIN_KEY` | 空 | 凭据加密密钥。**留空会自动生成并存到数据目录** |
| `DISABLE_BROWSER` | 空 | 设为 `1` 则完全禁用浏览器功能 |
| `LOG_LEVEL` | `info` | 日志级别 |

### 关于凭据加密

站点密码、DeepSeek API Key、WebDAV 密码都会用 **Fernet（AES）加密**后写入
`DATA_DIR/config.json`，文件权限 600。

密钥来源：
- 设了 `AUTOCHECKIN_KEY` → 用它（**推荐**，方便重建容器/换机后仍能解密）
- 没设 → 首次启动自动生成 `DATA_DIR/secret.key`

生成一个固定密钥（单行，方便直接粘贴到任何终端）：

```bash
docker run --rm xinghe361/autocheckin:latest python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"
```

> ⚠️ 密钥丢了就解不开已保存的密码，需要重新填写。
